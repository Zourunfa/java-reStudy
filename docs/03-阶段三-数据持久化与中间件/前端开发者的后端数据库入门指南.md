# 前端开发者的后端数据库入门指南

> 面向有 JavaScript / TypeScript、Vue 或 React
> 开发经验的前端工程师。目标不是一口气成为
> DBA，而是能看懂后端数据流、写基础
> SQL、理解索引和事务，并能与后端协作、排查常见问题。
>
> 示例以 **MySQL 8.x + InnoDB**
> 为主。不同数据库（PostgreSQL、SQLite、SQL Server
> 等）的语法和实现细节可能不同。

## 学习路线一览

建议按顺序学习，每个阶段都动手操作：

1.  **数据库是什么**：数据库、表、行、列、主键、外键。
2.  **SQL 基础**：查询、条件、排序、分页、增删改。
3.  **表设计**：数据类型、约束、关系、规范化。
4.  **索引**：为什么查询快、联合索引、EXPLAIN。
5.  **事务**：ACID、提交与回滚。
6.  **并发控制**：隔离级别、MVCC、快照读、当前读、锁、死锁。
7.  **后端接口如何访问数据库**：参数化查询、连接池、事务边界、错误处理。
8.  **实战项目**：完成一个简单的商品与订单系统。

## 第 1 章：先建立正确的整体认知

一个常见 Web 应用的数据流如下：

``` text
浏览器 / 前端
    |
    | HTTP 请求，例如 GET /api/products/1
    v
后端服务（Node.js / Java / Go 等）
    |
    | SQL 查询或 ORM 调用
    v
数据库（MySQL）
    |
    | 返回结果
    v
后端处理权限、业务规则、数据格式
    |
    | JSON 响应
    v
前端渲染页面
```

前端通常不应该直接连接生产数据库。数据库账号、密码和访问权限必须由服务端管理；前端通过
API 获取数据。

### 数据库的几个基本概念

  ----------------------------------------------------------------------------------
  概念                    通俗解释                           示例
  ----------------------- ---------------------------------- -----------------------
  数据库（Database）      一组相关数据的容器                 `shop`

  表（Table）             类似一张结构固定的电子表格         `users`、`products`

  行（Row）               一条记录                           某个用户

  列（Column）            记录的一个字段                     `id`、`name`

  主键（Primary Key）     唯一标识一条记录                   `users.id`

  外键（Foreign Key）     用约束表达表之间的引用关系         `orders.user_id`
                                                             指向用户

  索引（Index）           帮数据库更快定位数据的数据结构     `products(name)`

  事务（Transaction）     把一组数据库操作作为一个整体处理   创建订单并扣库存
  ----------------------------------------------------------------------------------

### 数据库和前端对象有什么不同？

前端的对象可以随意添加属性：

``` ts
const user = { id: 1, name: "小王" }
user.nickname = "阿王"
```

关系型数据库中的表通常预先定义列、类型和约束。要新增字段，一般需要执行数据库迁移（migration），而不是直接给某一条记录加属性。

## 第 2 章：安装与练习环境

入门建议使用本地 MySQL 8.x，并配合一个数据库客户端，例如 MySQL
Workbench、DBeaver 或命令行。也可以使用 Docker 启动测试数据库。

**安全提醒：**
只在本地或测试数据库练习。不要把真实生产库密码写进前端代码、Git
仓库或公开文档，也不要在不了解影响时执行 `DROP`、`DELETE` 或大范围
`UPDATE`。

连接数据库后，先查看版本：

``` sql
SELECT VERSION();
```

创建练习数据库：

``` sql
CREATE DATABASE learning_db
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;

USE learning_db;
```

如果你的 MySQL 版本不支持 `utf8mb4_0900_ai_ci`，可使用当前版本支持的
`utf8mb4` 排序规则。

## 第 3 章：创建一张表，理解数据类型

创建商品表：

``` sql
CREATE TABLE products (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  name VARCHAR(100) NOT NULL,
  price DECIMAL(10, 2) NOT NULL,
  stock INT NOT NULL DEFAULT 0,
  status TINYINT NOT NULL DEFAULT 1,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id)
);
```

字段说明：

-   `BIGINT`：较大范围的整数；`UNSIGNED` 表示不使用负数范围。
-   `AUTO_INCREMENT`：插入记录时自动生成递增 ID。
-   `VARCHAR(100)`：可变长度字符串，最多 100 个字符。
-   `DECIMAL(10, 2)`：适合保存金额等需要精确小数的值；不要用浮点类型直接存钱。
-   `INT`：整数，适合库存等数量。
-   `NOT NULL`：字段不能为 `NULL`。
-   `DEFAULT 0`：未指定时使用默认值。
-   `PRIMARY KEY`：主键，唯一标识记录。

插入一些测试数据：

``` sql
INSERT INTO products (name, price, stock, status)
VALUES
  ('机械键盘', 299.00, 20, 1),
  ('无线鼠标', 99.90, 50, 1),
  ('显示器', 899.00, 8, 1),
  ('旧款耳机', 59.00, 0, 0);
```

查看表结构和数据：

``` sql
DESCRIBE products;

SELECT * FROM products;
```

### `NULL` 不等于 0，也不等于空字符串

-   `0` 是一个数字。
-   `''` 是一个空字符串。
-   `NULL` 表示缺失、未知或未提供的值。

判断空值要写：

``` sql
SELECT * FROM products WHERE stock IS NULL;
```

不要写 `stock = NULL`，因为 SQL 对 `NULL` 使用三值逻辑。

## 第 4 章：SQL CRUD------后端每天都在做的事

CRUD 是 Create、Read、Update、Delete 的缩写。

### 4.1 查询 SELECT

``` sql
-- 查询全部字段（学习时方便；生产代码通常明确列出字段）
SELECT * FROM products;

-- 只取需要的字段
SELECT id, name, price
FROM products;

-- 条件查询
SELECT id, name, price
FROM products
WHERE price < 300 AND status = 1;

-- 排序
SELECT id, name, price
FROM products
ORDER BY price DESC;

-- 分页
SELECT id, name, price
FROM products
ORDER BY id
LIMIT 10 OFFSET 0;
```

注意：没有 `ORDER BY`
时，结果顺序不保证稳定。分页查询最好使用确定的排序字段。数据量很大时，深分页可考虑基于游标或最后一个
ID 的分页方式。

### 4.2 新增 INSERT

``` sql
INSERT INTO products (name, price, stock)
VALUES ('USB-C 转接头', 39.90, 100);
```

最好明确写列名，避免表结构变化后按隐含列顺序插入出错。

### 4.3 修改 UPDATE

``` sql
UPDATE products
SET price = 279.00
WHERE id = 1;
```

**一定要检查 `WHERE` 条件。** 忘记写 `WHERE`，可能会修改全表数据。

### 4.4 删除 DELETE

``` sql
DELETE FROM products
WHERE id = 4;
```

删除操作同样需要谨慎。生产环境中常见逻辑删除，例如增加 `deleted_at`
字段或 `is_deleted` 标记，但逻辑删除也需要统一查询规则和唯一性设计。

### 4.5 聚合与分组

``` sql
SELECT COUNT(*) AS product_count FROM products;

SELECT status, COUNT(*) AS total
FROM products
GROUP BY status;

SELECT MIN(price), MAX(price), AVG(price)
FROM products;
```

常见聚合函数：`COUNT`、`SUM`、`AVG`、`MIN`、`MAX`。

### 4.6 JOIN：关联多张表

订单和用户通常分开存储：

``` sql
SELECT
  o.id AS order_id,
  o.total_amount,
  u.name AS user_name
FROM orders AS o
JOIN users AS u ON u.id = o.user_id;
```

-   `INNER JOIN` / `JOIN`：只返回两边能匹配的记录。
-   `LEFT JOIN`：保留左表全部记录，右表没有匹配时右侧字段为 `NULL`。

把所有信息塞进一张大表并不总是好事。拆表能减少重复，但查询相关数据时可能需要
JOIN。

## 第 5 章：设计表------先想清楚数据之间的关系

一个简化的电商模型：

``` text
users  1 -------- N  orders
orders 1 -------- N  order_items
products 1 ------ N  order_items
```

含义：

-   一个用户可以有多笔订单。
-   一笔订单可以有多个订单商品。
-   一个商品可以出现在很多订单明细中。

创建用户和订单表示例：

``` sql
CREATE TABLE users (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  name VARCHAR(80) NOT NULL,
  email VARCHAR(255) NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_users_email (email)
);

CREATE TABLE orders (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_id BIGINT UNSIGNED NOT NULL,
  status TINYINT NOT NULL DEFAULT 1,
  total_amount DECIMAL(10, 2) NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_orders_user_created (user_id, created_at),
  CONSTRAINT fk_orders_user
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

### 设计时要思考

1.  **主键**：怎样唯一标识每条记录？
2.  **唯一约束**：哪些值不能重复？例如邮箱、业务订单号。
3.  **非空约束**：哪些字段必须存在？
4.  **默认值**：缺省时应该是什么？
5.  **关系**：一对一、一对多还是多对多？
6.  **数据生命周期**：是否允许删除？是否需要保留审计记录？
7.  **金额和时间**：使用合适的数据类型，明确时区与精度规则。

前端表单校验能改善用户体验，但不能替代数据库约束。因为请求可能来自脚本、其他客户端或恶意调用。

## 第 6 章：索引------为什么有时查询快，有时慢？

索引可以理解为书的目录。没有目录时，数据库可能需要逐条检查很多记录；有合适索引时，可以更快定位目标。

### 6.1 创建索引

``` sql
-- 给商品名称建立普通索引
CREATE INDEX idx_products_name ON products(name);

-- 查看索引
SHOW INDEX FROM products;
```

索引并非越多越好。索引会占用空间，而且插入、更新、删除时通常也需要维护索引。

### 6.2 联合索引

``` sql
CREATE INDEX idx_products_status_price
ON products(status, price);
```

这个联合索引的列顺序很重要。通常可以有效支持：

``` sql
WHERE status = 1
WHERE status = 1 AND price < 300
```

但通常不能像预期一样直接高效支持只按 `price`
过滤的查询，因为联合索引首先按 `status`
排序。这就是常说的**最左前缀原则**。实际效果还受数据分布、查询条件和优化器选择影响。

### 6.3 用 EXPLAIN 看执行计划

``` sql
EXPLAIN
SELECT id, name, price
FROM products
WHERE status = 1 AND price < 300;
```

入门先关注：

-   `type`：访问方式；`ALL` 通常意味着全表扫描，但不代表一定有问题。
-   `key`：优化器选择的索引。
-   `rows`：估算需要检查的行数。
-   `Extra`：额外执行信息，例如是否需要额外排序。

不要机械地认为"用了索引就一定快"。如果要取出大部分表数据，扫描全表可能更合适。要结合真实数据量、执行计划和耗时判断。

### 6.4 索引设计的常见思路

-   为主键、唯一业务标识建立合适约束或索引。
-   经常用于 `WHERE`、JOIN、排序和分组的字段值得评估。
-   联合索引按常见查询模式设计列顺序。
-   避免滥建索引。
-   对慢查询先用 `EXPLAIN` 分析，再考虑调整。

## 第 7 章：事务与 ACID

事务把多条数据库操作组织成一个整体。典型例子是创建订单并扣减库存。

ACID：

-   **A --- Atomicity（原子性）**：事务中的操作作为整体提交或回滚。
-   **C --- Consistency（一致性）**：事务前后应满足业务和数据库约束。
-   **I --- Isolation（隔离性）**：并发事务之间按隔离规则互相影响。
-   **D ---
    Durability（持久性）**：提交成功后，数据应按数据库的持久化保证保存。

### 7.1 提交与回滚

``` sql
START TRANSACTION;

UPDATE products
SET stock = stock - 1
WHERE id = 1 AND stock > 0;

-- 应用程序需要检查更新是否成功；失败时不能继续创建有效订单
-- 在确认所有业务条件满足后再提交
COMMIT;

-- 如果业务失败且事务尚未提交，可执行：
-- ROLLBACK;
```

注意：SQL 示例里的注释代表应用层需要进行的判断。单靠上面这几条 SQL
并没有自动实现完整的订单业务。实际系统需要检查库存更新影响行数、插入订单和订单明细，并在适当时机提交或回滚。

### 7.2 用条件更新防止重复操作

``` sql
UPDATE orders
SET status = 2
WHERE id = 1001 AND status = 1;
```

这表达了"只有订单仍处于待处理状态时才允许改变状态"的规则。

应用程序要检查受影响行数：

-   `1`：通常表示匹配并修改了一行。
-   `0`：可能是订单不存在，也可能是状态不再符合条件；需要按业务规则处理。

这是乐观并发控制的一种常见写法，体现 CAS（比较并交换）的思想。

## 第 8 章：隔离级别、MVCC 与锁

这部分不必第一天全部背熟，先建立整体图景。

### 8.1 四种隔离级别

  -------------------------------------------------------------------------------------------------
  隔离级别                通俗理解                               InnoDB 常见表现
  ----------------------- -------------------------------------- ----------------------------------
  READ UNCOMMITTED（RU）  可能看到别人尚未提交的数据             可能发生脏读

  READ COMMITTED（RC）    每次一致性读通常看一个新的已提交视图   同一事务两次查询可能读到不同结果

  REPEATABLE READ（RR）   普通一致性读通常复用同一快照           InnoDB 默认隔离级别

  SERIALIZABLE            对并发施加更严格限制                   并发能力通常更低
  -------------------------------------------------------------------------------------------------

术语：

-   **脏读**：读到另一个事务尚未提交、之后可能回滚的数据。
-   **不可重复读**：同一事务重复读取同一行，结果发生变化。
-   **幻读**：同一查询条件再次执行时，出现符合条件的新增或消失记录。

### 8.2 MVCC 和 ReadView

MVCC 是多版本并发控制。数据库借助 Undo Log
等机制保留或重建历史版本，让读取操作可以读取符合可见性规则的版本，而不总是与写入操作互相阻塞。

ReadView
可以理解为"版本可见性规则"，它决定当前一致性读能看到哪些事务产生的数据版本。

InnoDB 的 RC 通常为每次一致性读创建新的 ReadView；RR
通常在本事务第一次一致性读时创建，并由后续一致性读复用。具体行为应以数据库版本和语句类型为准。

### 8.3 快照读和当前读

``` sql
-- 普通一致性读：在 RC / RR 下通常是快照读
SELECT stock FROM products WHERE id = 1;

-- 当前读：查询并锁定记录
SELECT stock FROM products WHERE id = 1 FOR UPDATE;

-- UPDATE / DELETE 通常也涉及当前版本读取与加锁
UPDATE products SET stock = stock - 1 WHERE id = 1;
```

通俗地说：

-   快照读：像查看一张符合事务可见性规则的旧照片。
-   当前读：读取当前可用的记录版本，并根据操作需要加锁。

所以在 RR 事务里，普通 `SELECT` 读到旧值，而后续 `SELECT ... FOR UPDATE`
读到更新后的当前值，可能是正常现象；两种语句的读取语义不同。

### 8.4 三类常见锁

-   **记录锁（Record Lock）**：锁定索引记录。
-   **间隙锁（Gap Lock）**：限制在特定索引间隙插入记录。
-   **Next-Key Lock**：记录锁与前方间隙锁的组合。

锁定范围不单由 `WHERE`
条件决定，还取决于实际使用的索引、扫描范围、执行计划和隔离级别。缺少合适索引可能扩大扫描与锁定范围，造成很多事务等待。

### 8.5 死锁

死锁的典型场景：

-   事务 A 持有资源 1，等待资源 2。
-   事务 B 持有资源 2，等待资源 1。

InnoDB 通常能检测死锁并回滚其中一个事务。排查可以查看：

``` sql
SHOW ENGINE INNODB STATUS;
```

重点查看 `LATEST DETECTED DEADLOCK` 部分。

降低死锁影响的办法：

1.  所有事务尽量按相同顺序访问资源，例如按 ID 升序更新。
2.  事务尽量短，不要在持锁时等待很慢的外部操作。
3.  为常用条件设计合适索引，减少无谓扫描。
4.  应用层针对死锁错误进行有限次数、安全的事务重试。

## 第 9 章：从前端看后端数据库调用

前端可能发出：

``` ts
const response = await fetch("/api/products?page=1&pageSize=10")
const result = await response.json()
```

背后可能是：

``` text
前端 fetch
  -> 后端路由 / Controller
  -> 参数校验与权限验证
  -> Service 业务逻辑
  -> Repository / ORM / SQL
  -> MySQL
  -> 后端组装 JSON
  -> 前端渲染
```

### 前端开发者需要特别理解的 5 件事

1.  **前端校验不是安全边界。** 后端必须重新校验参数和权限。
2.  **不要信任前端传来的价格、用户 ID、订单状态。**
    服务端应从可信来源计算或验证。
3.  **数据库查询必须参数化。** 不要把用户输入直接拼进 SQL 字符串。
4.  **分页、排序、筛选要有后端约束。** 不要允许客户端随意传入未验证的
    SQL 字段或排序表达式。
5.  **接口成功不等于所有外部副作用都成功。**
    数据库提交、消息发送、支付和物流可能需要可靠的补偿或一致性方案。

### 参数化查询示例（Node.js mysql2）

以下是概念示例，实际项目还需补充连接配置、错误处理和资源释放：

``` ts
const [rows] = await pool.execute(
  "SELECT id, name, price FROM products WHERE status = ? AND price < ?",
  [1, 300]
)
```

`?` 是参数占位符，值由数据库驱动安全地传入。参数化查询是防止 SQL
注入的基本措施之一。表名、列名等 SQL
结构通常不能直接用普通值占位符替代，需要通过白名单控制。

### ORM 是什么？

ORM（对象关系映射）让开发者可以用语言中的对象和方法操作数据库，例如
Prisma、TypeORM、Sequelize。它可以减少重复
SQL，但不会自动消除所有数据库问题。仍然需要理解索引、事务、查询数量、锁和执行计划。

## 第 10 章：实战练习------做一个小型商品订单系统

### 目标

实现商品列表、商品详情、创建订单、扣减库存、查询订单状态。

### 建议数据表

-   `users`：用户
-   `products`：商品、价格、库存
-   `orders`：订单主信息
-   `order_items`：订单商品明细

### 练习任务

**初级：SQL 基础**

-   [ ] 创建 `products` 表并插入 5 条测试数据。
-   [ ] 查询价格低于 300 的上架商品。
-   [ ] 按价格降序排序并分页。
-   [ ] 查询每种商品状态的数量。
-   [ ] 用 JOIN 查询订单和用户名称。

**中级：表设计与索引**

-   [ ] 为用户邮箱添加唯一约束。
-   [ ] 为订单的 `user_id`、`created_at` 查询模式设计索引。
-   [ ] 使用 `EXPLAIN` 比较查询计划。
-   [ ] 思考为什么 `(status, price)` 与 `(price, status)` 不完全相同。

**进阶：事务与并发**

-   [ ] 创建订单时，在同一事务中检查并扣减库存、写入订单和订单明细。
-   [ ] 使用 `UPDATE ... WHERE stock >= ?` 防止库存扣成负数。
-   [ ] 检查更新影响行数，库存不足时回滚。
-   [ ] 用两个数据库会话模拟并发扣库存。
-   [ ] 用两个事务模拟相反顺序更新记录，观察死锁并尝试修复。

库存扣减的关键思路：

``` sql
UPDATE products
SET stock = stock - 2
WHERE id = 1 AND stock >= 2;
```

应用程序应检查影响行数。只有库存扣减成功，才继续写订单；订单及明细写入失败时，应回滚整个数据库事务。实际系统还要考虑幂等性、重复提交、支付超时和订单取消后的库存返还。
