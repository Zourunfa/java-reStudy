# 为什么 MySQL 索引用 B+ 树，而 Redis 的 Sorted Set 会用跳表？

## 一句话结论

**MySQL 更关注磁盘 I/O 和范围查询；Redis
更关注内存中的有序操作和实现效率。** B+ 树和跳表适合不同的场景。

-   **B 树**：一个节点可以存多个键，查找时逐层向下。
-   **B+ 树**：类似 B
    树，但数据主要集中在叶子节点，叶子节点通常按顺序连接。
-   **跳表**：给有序链表增加多层索引，让查找可以跳跃前进。
-   **哈希**：通过哈希函数计算数据的位置，平均情况下可以快速查找。

------------------------------------------------------------------------

## 一、为什么 MySQL 选择 B+ 树？

假设 MySQL 有一张用户表，存储了 100 万条用户数据：

``` sql
SELECT * FROM user WHERE id = 888888;
```

如果 `id` 建立了索引，MySQL 就不需要扫描全部 100
万条记录，而是可以通过索引快速定位。

### 1. 为什么不用普通二叉搜索树？

普通二叉搜索树每个节点最多只有两个子节点。如果树比较高，查找过程中就可能需要访问很多节点。

B+
树的一个节点可以保存很多键，并拥有很多子节点，因此树的高度通常比较低。

举个简化的例子：

-   假设每层平均有 100 个分支。
-   3 层可以覆盖约 `100³ = 1,000,000` 个索引位置。

这只是帮助理解的理想化示例，不是所有 B+ 树的实际参数。

**树越矮，查询过程中通常需要读取的索引页就越少。**

### 2. 为什么不用哈希索引？

哈希索引查找单个键很快，但它不擅长范围查询。

例如：

``` sql
SELECT * FROM user
WHERE id BETWEEN 1000 AND 2000;
```

B+ 树可以先定位到 `1000` 附近的叶子节点，再沿着有序的叶子节点向后扫描。

哈希索引无法直接利用键的大小顺序来完成这种范围遍历。

### 3. 为什么 B+ 树比 B 树更适合数据库索引？

主要有三个原因：

-   **内部节点可以存更多索引键**：不需要在每个内部节点都保存完整数据记录时，通常可以提高分支数量。
-   **树高较低**：可以减少查找过程中的索引页访问。
-   **范围查询高效**：所有数据记录或记录指针集中在叶子层，叶子节点通常按顺序连接。

在 MySQL InnoDB 中：

-   主键索引的叶子节点存储完整的行数据。
-   二级索引的叶子节点存储索引键和对应的主键值。

## 二、Redis 为什么使用跳表？

Redis 是以内存为主要工作场景的数据存储系统，Sorted
Set（有序集合）需要支持按分数排序和查询。

例如排行榜：

  用户     分数
  ------ ------
  小明       60
  小红       75
  小刚       88
  小李       95
  小王       99

现在想查询分数在 80 到 100 之间的用户。

Redis 的 Sorted Set 需要支持有序插入、按排名查询以及分数范围查询等操作。

### 1. 普通链表有什么问题？

如果使用普通有序链表，查找分数为 95 的用户，可能需要从头遍历：

``` text
60 → 75 → 88 → 95 → 99
```

数据量越大，遍历成本越高，查询复杂度为 `O(n)`。

### 2. 跳表如何解决？

跳表为有序链表增加多层索引。

查找时：

1.  从较高层开始，快速跨过一部分节点。
2.  如果下一个节点超过目标值，就向下一层。
3.  不断缩小范围，最终定位到目标节点。

跳表的平均查找复杂度为 `O(log n)`。

跳表还有几个优点：

-   插入、删除时，不必像某些平衡树那样进行复杂的旋转调整。
-   能保持数据有序，适合范围查询。
-   实现思路相对直观，适合 Redis 的内存数据结构设计。

注意：跳表的 `O(log n)` 是平均意义上的复杂度，最坏情况下仍可能退化到
`O(n)`。

------------------------------------------------------------------------

## 三、B+ 树和跳表有什么区别？

  对比项     B+ 树            跳表
  ---------- ---------------- --------------------------------
  核心结构   多路平衡搜索树   多层有序链表
  典型场景   数据库索引       内存有序集合
  平均查找   `O(log n)`       `O(log n)`
  范围查询   非常适合         非常适合
  主要优势   减少索引页访问   结构相对简单，维护有序数据方便

### B+ 树

**优化目标：减少磁盘页访问。**

节点可以存很多键，树的高度较低，适合数据库索引。

### 跳表

**优化目标：高效维护内存中的有序数据。**

利用多层链表索引加速查找，插入、删除逻辑相对简单。

注意：不是说 B+
树只能用于磁盘，也不是说跳表只能用于内存。两者的设计取舍不同，实际性能还取决于数据规模、访问模式和实现方式。

## 四、Redis 为什么不用哈希表实现 Sorted Set？

因为哈希表擅长按键查找，却不能天然维护分数的顺序。

  需求                      更适合的结构
  ------------------------- --------------
  按用户 ID 查找用户        哈希表
  查询分数最高的用户        有序结构
  查询分数 80～100 的用户   有序结构
  查询某用户的排名          有序结构

Redis 的 Sorted Set 在使用跳表的编码实现中，会将哈希表与跳表配合使用：

-   **哈希表**：根据成员快速定位分数。
-   **跳表**：根据分数维护顺序，支持范围查询和排名操作。

另外，Redis 会根据 Sorted Set
的大小等条件选择不同编码；小型集合可以使用更紧凑的结构，并不是所有
Sorted Set 都始终使用跳表。

## 五、面试回答模板

> B 树和 B+ 树都是多路平衡搜索树，适合有序索引。B+
> 树的内部节点主要存储索引信息，叶子节点集中保存记录或记录指针，并且叶子节点通常相连，因此非常适合数据库索引和范围查询。
>
> 跳表通过多层索引加速有序链表的查找，平均查询复杂度是
> `O(log n)`，实现相对简单，Redis 的 Sorted Set 会使用它。
>
> 哈希表通过哈希函数将键映射到存储位置，平均查询、插入和删除复杂度为
> `O(1)`，但存在哈希冲突，也不适合直接进行有序范围查询。

### 速记卡

-   **B 树**：多路平衡查找。
-   **B+ 树**：数据库索引、范围查询。
-   **跳表**：有序链表 + 多层索引。
-   **哈希**：按键快速定位，不保证顺序。

## 六、练习题

**问题：** 如果要查询数据库中 `id` 从 1000 到 2000 的所有记录，为什么 B+
树通常比哈希索引更合适？

A. 因为 B+ 树的所有查找都是 `O(1)`。

B. 因为 B+ 树按键有序，可以定位起点后连续遍历叶子节点。

C. 因为哈希表不能查找任何数据。

D. 因为 B+ 树不需要维护索引。

**正确答案：B。**

B+
树能够利用键的有序性，先定位范围起点，再沿叶子节点扫描。哈希索引适合精确键查找，但无法直接利用键的顺序完成范围扫描。
